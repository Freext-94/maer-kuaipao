> 基础：在 `docs/需求与改造计划.md`（v2）上增量，已并入主计划 v3；本轮 11 条（R1–R11）全部来自原型实测与后续确认。

## 0. 先说结论

用户已确认 5 个口径：

| 问题 | 决定 |
|---|---|
| 多商家取货 | **全部取齐才能配送**；不允许取一家先送一家 |
| 自由填商家 | **建「待完善商家」记录**，不只是一段文字；调度台补类目/电话/地址后转正式 |
| 今天跑腿费 | **按北京时间 0 点结算**；即 Asia/Shanghai 当日 00:00–24:00 |
| 收款方式 | **结单/送达后收款**；微信、支付宝、现金、欠款；欠款计入该客户账单 |
| 商家类目 | **多选**；类目可新增；商家档案可新增自定义字段 |

这 11 条有 **3 个结构性改造** 和 **2 个跨端改造**：

| 类型 | 条目 | 影响 |
|---|---|---|
| 结构性改造 | R1 一单多商家、待完善商家 | `t_order` 从"一单一商家"变成"一单多商家组"；备货、垫付、取货、账单按组拆 |
| 结构性改造 | R9 商家并入用户表、类目多选、自定义字段 | 商家账号 = 用户 + 商家角色 + 门店档案；类目多对多；商家字段可配 |
| 结构性改造 | R8 服务类型后台可加、可传 icon、可配表单 | 服务类型从硬编码变成 `t_service_type + form_schema`，订单存表单快照 |
| 跨端改造 | R10 移动端优先 | 调度台也以手机为主；表格改卡片、弹窗改全屏、底部导航与操作条 |
| 跨端改造 | R11 账单出图 | 生成 PNG 图片，不生成 PDF；手机直接分享/保存 |

其余 6 条（R2 改单/补商家、R3 0 元取货、R4 口语化、R5 收款方式、R6 账单页、R7 累计收回）是流程、口径和文案改造，不改钱账不变式。

工作量粗估（不含联调/验收）：**R1 XL、R2 M、R3 S、R4 S、R5 S、R6 M、R7 S、R8 L、R9 L、R10 L、R11 S**。R1/R8/R9/R10 建议各自独立批次，不要混做。

## 1. 逐条方案

### R1 客户代买：搜不到商家可自己填；一单可多个商家、多件物品

**原型现状**
- 客户端代买只能从已有商家里选一个；搜不到就下不了单。
- 一单只能有一个商家、一段"买什么"。

**目标**
- 搜不到商家时，可以直接填商家名（可选填电话），继续下单。
- 一单可以添加多个商家；每个商家下面可以填多件物品；订单总额按商家组汇总。
- 电话录单同样支持，保持两端一致。

> 为什么不拆成多个订单：客户只下一次单、只付一次跑腿费、只对一张账单；骑手一次取多店。拆单会让派单、账单、欠款碎片化。

**数据模型（核心改动）**

新增 `t_order_merchant`（订单商家组）：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `order_id` | 订单 |
| `seq` | 第几家店，1、2、3… |
| `merchant_id` | 已建档/待完善商家；自由填写时指向 pending 记录 |
| `merchant_name` | 商家名快照（自由填写时就是客户写的名字） |
| `merchant_phone` | 商家电话，可空 |
| `merchant_category` | 类目快照，可空 |
| `source` | `existing` 已建档 / `manual` 自由填写 / `pending` 待完善 |
| `prep_status` | `not_needed` / `notified` / `ready` / `silent` / `cancelled` |
| `notified_at` / `ready_at` | 备货时间 |
| `goods_est_fen` / `goods_real_fen` | 该店货款估价/实付；实付 `0` 合法，`NULL` 表示未录 |
| `picked_at` | 该店取货时间 |
| `receipt_attachment_id` | 该店小票，0=无 |
| `note` | 该店备注 |

配套改动：
- `t_order_item` 增加 `order_merchant_id`，每件物品挂到某个商家组。
- `t_order.goods_est_fen / goods_real_fen` 变成**所有组的合计**，不再代表单一商家。
- `t_advance` 增加 `order_merchant_id`，垫付按组记；唯一键从 `order_id` 改为 `order_merchant_id`。
- 备货状态收口到 `t_order_merchant`：`prep_status / notified_at / ready_at / shortage / shortage_text / acked_channel`；`t_merchant_prep` 数据在 V4 迁入组后停用（旧表可保留只读）。
- `t_order.merchant_id` 保留为"主商家/兼容字段"（第一组），新逻辑以组为准。

**自由填商家怎么处理（已确认：待完善商家）**
- 客户/电话录单搜不到时，填商家名（可选电话）→ 自动建一条 **待完善商家**：`t_merchant.status='pending'`，只存名字/电话/来源订单。
- 订单组 `merchant_id` 指向这条 pending 记录；订单可以继续走，不阻塞。
- 待完善商家**不进常规商家搜索**（电话录单/客户端只列 active），只在「商家管理 → 待完善」里出现，避免被别的客户误选。
- 调度台在订单详情点「补全商家」：补类目（多选）、电话、地址，保存后转 `active`；同名/同电话已存在则合并，不重复建。
- 有电话就可以发备货通知；没有电话 `prep_status=not_needed`，骑手直接去买。
- 客户写的是已有商家别名时，搜索匹配优先；匹配不到才走待完善。

**流程**
- 创建：至少一个商家组；每组至少一件物品。
- 派单：
  - 有电话/已建档的组 → 写组的备货状态，并落 `t_notify_record` 通知。
  - 无电话的自由填写组 → `not_needed`，不通知。
  - 所有组都不需要备货 → 派单后直接 `READY_FOR_PICKUP`。
- 取货：按组录实付（0 合法）+ 小票；取货顺序按 `seq`；所有组取齐后订单才进 `PICKED_UP`。
- 商家端只返回自己那一组，不展示其它店的商品/金额；骑手端和客户端看全部组。
- 部分取齐：订单保持 `READY_FOR_PICKUP`，详情显示"已取 1/2 家"；不允许开始配送，直到全部取齐。
- 账单：按组列货款，合计进订单账单。

**接口**
- `OrderCreateCmd` 增加 `merchantGroups[]`：
  ```json
  [{
    "merchantId": 1,
    "merchantName": "瑞雪生鲜超市",
    "merchantPhone": "0769-...",
    "items": [{"goodsText":"西瓜 3 个","qty":1,"estFen":6000}],
    "goodsEstFen": 6000,
    "note": ""
  }]
  ```
- 兼容旧字段：只传 `merchantId + goodsText + goodsEstFen` 时，后端自动包成一组。
- `OrderView` 增加 `merchantGroups[]`；旧的 `merchantName/merchantPhone` 取第一组，避免前端全部重写。
- `POST /api/admin/orders/{id}/merchant-groups` 追加一组；`PATCH .../{groupId}` 修改；`DELETE` 仅在未取货时允许。
- 取货接口改为按组：`POST /api/admin/orders/{id}/merchant-groups/{groupId}/pickup`。

**验收**
- 客户一单填 2 家店、3 件物品，提交成功；调度台看到 2 个商家组。
- 商家 A/B 各自只看到自己那组，互不串单。
- 骑手分别录两家的实付（一家 92.40、一家 0），订单账单合计正确。
- 自由填写"楼下王记水果"（无电话）→ 生成待完善商家，能下单、不产生通知；调度台补类目/电话后转正式，客户搜索里仍不出现未完善商家。

**风险**
- 最大的一次模型改造；`t_advance` 的唯一键、商家端查询、账单都要跟着改。
- 部分取货、部分缺货、部分取消先不做；一期只支持"全部取齐"，缺货走整单取消或备注。

### R2 调度台支持修改订单；没有商户的订单可以补商户

**原型现状**
- 订单建好后不能改，只能取消重录。
- 客户自助单/服务单可能没有商家，调度台没有补录入口。

**目标**
- 调度台在订单详情里可以编辑订单。
- 没有商家的订单，可以补一个商家（或一组商家），补完继续走备货/取货。
- 每次修改留痕，谁改了什么、为什么改，能倒查。

**可编辑范围（按状态硬限制）**

| 状态 | 允许改 | 不允许改 |
|---|---|---|
| 待派单 / 待备货 / 备货完成 | 客户、地址/联系人、期望时间、备注、商家组/物品/估价、跑腿费、附加费、优惠、服务表单 | 单号、来源、创建人、已产生的钱账 |
| 已取货 / 配送中 | 地址/联系人、期望时间、备注、服务表单中的非金额字段 | 客户、商家组、物品、货款、跑腿费 |
| 已送达 | 备注 | 其它 |
| 已结单 / 已取消 | 不允许改 | 只能走冲正/减免/收款 |

**补商户**
- 只对代买/需要备货的服务类型显示；代驾、接送等不需要商家的类型不显示。
- 订单没有商家组时，详情页显示「补充商家」。
- 补商家时可以：
  - 选已有商家（搜索）；
  - 新建商家（店名、类目、电话、地址）；
  - 自由填写（只写名字/电话，生成待完善商家）。
- 补完后如果是代买，按组创建备货通知；如果是无电话自由填写，`not_needed`。

**修改商家/金额后的处理**
- 派单后换商家：旧组若未取货，把旧组 `prep_status` 置 `cancelled`；新组重新通知；订单回到 `PENDING_PREP`。
- 派单后改物品/估价：允许，但留痕；已取货的组不允许改。
- 已产生垫付的组不允许删除；要取消走整单取消并清算垫付。
- 已结单后不允许改金额；只能新增冲正/减免流水。

**审计**
- 新增 `t_order_edit_log`：
  `id, order_id, editor, at, action, before_json, after_json, reason`。
- 订单详情时间线显示"修改订单：地址、跑腿费 8→10、补商家 瑞雪"。
- 权限码 `order.edit`，默认给管理员；骑手不给。

**接口**
- `PUT /api/admin/orders/{id}`，请求体 `OrderEditCmd`，字段全部可选，服务端按状态白名单校验。
- `POST /api/admin/orders/{id}/merchant-groups`（补商家/加组）。
- `GET /api/admin/orders/{id}/edit-logs`。

**验收**
- 客户自助单没商家 → 调度台补"康民药店" → 药店收到备货通知 → 正常取货。
- 派单后改地址/跑腿费 → 保存成功 → 时间线有修改记录。
- 已取货后改货款 → 被拒绝，提示走"货款不对"。
- 已结单后改金额 → 被拒绝。

**风险**
- 编辑和状态机、通知、垫付耦合；必须在 Service 层做白名单，不能只靠前端隐藏。
- 改客户会影响欠款归属；只允许在未结单、且没有流水时改，并留痕。

### R3 取货登记可以 0 元

**原型现状**
- 代买单取货时前端/后端都要求货款 > 0；0 元提交不了。

**目标**
- 0 元是合法录入值，表示"商家没收钱/已预付/样品"。
- 0 元和"没录"必须区分：`0` 是已确认，`NULL` 是未录。

**改法**
- `goodsRealFen` 允许 `>= 0`；只有 `NULL` 才表示未取货/未录。
- `markPicked` 校验改为"必须提交，且 >= 0"；0 元写日志"实付 0 元（已确认无货款）"。
- 0 元不创建 `t_advance`；取消时也不需要垫付清算。
- 前端：输入框允许 0；提交 0 时二次确认"确认这单没有货款？"；账单显示 `¥0.00（已确认）`，不是"未录"。
- 多商家：每个商家组独立 0 元；订单合计可以为 0。

**验收**
- 代买单取货填 0 → 成功；账单货款 0.00、应收=跑腿费；取消不要求追回垫付。
- 0 元取货后不能再改；要改走"货款不对"。

**风险**
- 误填 0 会导致少记成本；二次确认 + 日志 + 账单显式标注，避免和"没录"混淆。

### R4 货款争议 / 冲正改成口语

**原型现状**
- 按钮叫「货款争议 / 冲正」，弹窗讲"冲正""减免""差额填负数"，骑手看不懂。

**目标**
- 前端全部用口语；"冲正/ADJUST/WAIVE"只留在数据库和开发文档里。
- 骑手/老板都能一眼知道自己该选哪个。

**文案方案**

| 现在 | 改成 |
|---|---|
| 货款争议 / 冲正 | **货款不对？** |
| 冲正（商家退差/补差） | **商家退我钱** / **我补给商家** |
| 减免（老板让客） | **给客户免掉** |
| 差额（元），退差填负数 | **差多少钱（元）**，只填正数 |
| 小票金额不改，只加一条冲正流水 | **小票金额不会改，只补一笔差额，月底对账能看到** |

**交互**
- 弹窗三个大按钮/单选项：
  1. 商家退我钱（应收减少）
  2. 我补给商家（应收增加）
  3. 给客户免掉（老板让利）
- 金额只填正数；系统按选项决定正负。
- 原因必填， placeholder 给例子："西瓜称重比小票少 4.40，商家退我"。
- 日志/账单显示"商家退钱 -4.40""补给商家 +2.00""给客户免掉 -10.00"。

**接口**
- 新增 `POST /api/admin/orders/{id}/adjust`：
  ```json
  {"direction":"merchant_refund|pay_merchant|waive","amountFen":440,"reason":"..."}
  ```
- 后端映射：
  - `merchant_refund` → `ADJUST`，-amount
  - `pay_merchant` → `ADJUST`，+amount
  - `waive` → `WAIVE`，-amount
- 旧 `deltaFen` 参数保留兼容，但新前端不再用。

**验收**
- 骑手/老板不看文档也能完成一次"商家退我 4.40"；账单应收减少 4.40，原小票金额不变。
- 三种方向各测一次，金额符号正确。

**风险**
- 方向映射写反会导致账错；Service 层单测覆盖三种方向，前端不直接算符号。
- 已结单且已收款的订单，退差后可能出现「已收 > 应收」；这时按退款/负余额处理，不改已收原值，避免把流水改乱。

### R5 结单/送达后收款：微信、支付宝、现金、欠款

**原型现状**
- 结单收款方式有微信/现金/支付宝/扫码，没有"欠款"。
- 实收 0 时只是不记收款，没有明确的"欠款"语义。

**目标**
- **已确认：结单/送达后收款，不做预付。**
- 收款方式固定四种：**微信、支付宝、现金、欠款**。
- 选欠款时，整单应收计入该客户账单（页面叫“客户账单”）。
- "欠款"不是一种支付，而是"这单现在不收钱，整单计入客户账单"。

**规则**
- 选微信/支付宝/现金：
  - 实收必须 > 0；
  - 可以小于应收，余额自动记欠款；
  - 收款流水记实际方式。
- 选欠款：
  - 实收必须 = 0；
  - 不产生收款流水；
  - 整单应收进该客户账单；
  - 订单记 `settle_method=credit`。
- 实收 > 应收：拒绝；多收走预收/另行登记（本期不做预收，直接拒绝）。

**数据**
- `t_order` 增加 `settle_method VARCHAR(16)`：`wechat/alipay/cash/credit`。
- `t_ledger_entry.method` 统一存代码，前端映射中文；历史值做一次迁移。
- 欠款不写 payment 流水，避免"0 元收款"污染流水。

**接口**
- `POST /api/admin/orders/{id}/finish` body `{paidFen, method}`。
- `method` 必填，枚举校验；`credit` 时 `paidFen` 必须 0。
- 骑手代收同一套规则。

**UI**
- 结单弹窗：方式四选一；选"欠款"时金额自动 0 且禁用；选其它方式时默认应收全额，可改小，下面提示"剩余 X 元计入账单"。
- 账单/流水显示"微信 / 支付宝 / 现金 / 欠款"。

**验收**
- 四种方式各结一单：微信/支付宝/现金产生对应流水；欠款不产生流水但账单金额增加。
- 部分收款（微信 50，应收 96）→ 流水 50，账单 46。
- 欠款 + 实收 50 → 被拒绝。

**风险**
- "欠款"和"部分收款"容易混；前端用"是否收到钱"引导，后端强校验。

### R6 订单账单 + 收款流水放一个页面；默认今天；按年月筛；分开货款/跑腿费；顶部三个数

**原型现状**
- 账单页用 Tab 分"订单账单/收款流水"，默认全部时间。
- 顶部是累计应收/已收/客户欠款/今日收款，不是本轮要的三个数。
- 表格没有把货款和跑腿费拆成独立列。

**目标**
- 一个页面同时看到订单账单和收款流水（上下两个区块，不再用 Tab 切换）。
- 默认今天；支持今天/昨天/本月/自定义年月。
- 订单表拆列：货款、跑腿费、附加费、优惠、应收、已收、未收。
- 顶部三个数：**今天跑腿费、昨天跑腿费、账单合计**（原“累计欠款”）。

**口径（建议）**
- **今天跑腿费** = 今天**结单**的订单的跑腿费合计（按 `finished_at`）。
- **今天/昨天按北京时间 0 点切**：Asia/Shanghai 当日 00:00–24:00；服务端统一用 `ZoneId.of("Asia/Shanghai")`，不要用服务器默认时区。
- **昨天跑腿费** = 北京时间昨天 00:00–24:00 结单的订单跑腿费合计。
- **账单合计** = 所有流水净额（未结账单总额），不是"今天新增账单"。
- 未结单的订单不计入今天跑腿费；如果要看预计值，在表格里另设"含进行中"开关。
- 如果老板习惯按"下单时间"算收入，改成 `created_at` 即可；这是唯一需要拍板的口径。

**页面结构**

> 顶部三个数固定按今天/昨天/全部时间算，不随下面的筛选变化；筛选只影响订单表和流水表。

```
[筛选：今天 | 昨天 | 本月 | 年月 ▼]  [客户/单号搜索]
[今天跑腿费] [昨天跑腿费] [账单合计]

订单账单（默认今天结单）
单号 | 结单时间 | 客户 | 货款 | 跑腿费 | 附加费 | 优惠 | 应收 | 已收 | 未收 | 状态
合计：货款 ¥… / 跑腿费 ¥… / 应收 ¥… / 已收 ¥… / 未收 ¥…

收款流水（同筛选区间）
时间 | 客户 | 单号 | 方式 | 金额 | 经办人 | 备注
合计：¥…
```

**接口**
- `GET /api/admin/billing/summary?date=YYYY-MM-DD` → `{todayServiceFeeFen, yesterdayServiceFeeFen, totalBillFen}`；按北京时间 0 点切日。
- `GET /api/admin/billing/orders?from&to&customerId&status&includeOpen`。
- `GET /api/admin/billing/payments?from&to&customerId&method`。
- 导出 CSV 包含两个区块。

**验收**
- 默认打开是今天（北京时间 0 点切）；今天结单 2 单，跑腿费合计正确；23:59 结单算今天，00:01 算明天。
- 切到 2026-11，订单和流水都按 11 月筛。
- 订单表货款/跑腿费分列，合计与流水一致。
- 账单合计与客户账单页合计一致。

**风险**
- 口径不统一会导致"今天跑腿费"和账单合计对不上；页面必须标注"按结单时间"。
- 时区统一 Asia/Shanghai；`finished_at` 存库时间，统计时按北京时间切日；服务器时区不是 +08:00 时要显式转换。

### R8 服务类型后台可新增；上传 icon；配置表单

**原型现状**
- 5 类服务写死在前端/后端；设置页只能启停和改默认费。
- 图标是固定 SVG 文件。

**目标**
- 后台可以新增服务类型，配置名称、图标、默认费、表单字段、流程类型、启停、排序。
- 新类型不需要改代码、不需要发版，就能出现在电话录单和客户端下单。
- 新增的服务类型可以按需要定义自己的字段（如宠物接送：宠物类型/体重/是否笼子）。

**数据模型**

`t_service_type`：

| 字段 | 说明 |
|---|---|
| `code` | 唯一英文标识，如 `pet_transfer`，创建后不可改 |
| `name` | 显示名，如"宠物接送" |
| `icon_path` | 上传的图标路径 |
| `form_kind` | 内置版式：`buy` 代买 / `route` 路线 / `driver` 代驾 / `blank` 纯自定义 |
| `form_schema` | JSON，额外字段定义 |
| `flow_kind` | `buy` 需备货 / `standard` 标准 / `scheduled` 预约 |
| `default_fee_fen` | 默认服务费 |
| `enabled` / `sort_no` | 启停/排序 |
| `schema_version` | 表单版本，订单存快照用 |

`t_order_service` 增加：
- `service_data JSON`：按 schema 填的值；
- `schema_snapshot JSON`：下单时的字段定义（含 label/type），保证历史订单显示不变。

**表单设计器**
- 字段类型首批 **8 种**（与服务类型表单共用）：单行文本、多行文本、数字、电话、日期、下拉单选、多选、开关。
- 每个字段配置：key（英文，自动生成可改）、label、类型、是否必填、placeholder、选项（下拉）、排序。
- 内置字段（客户、商家组、货款、跑腿费、骑手、附件、备注）不放进 schema，避免管理员把核心字段删掉；一期只允许加额外字段，不支持隐藏内置字段。
- `form_kind` 决定内置区块：
  - `buy`：商家组 + 物品 + 货款；
  - `route`：起点/终点/内容/预约时间/联系人；
  - `driver`：起点/终点/车牌/车型/预约时间；
  - `blank`：只有客户、费用、骑手等公共字段 + 自定义字段。
- 保存前预览；上线中的类型改 schema 只影响新单，旧单按快照渲染。

**图标上传**
- **已确认支持 SVG + WebP**，同时兼容 PNG/JPG；建议 96×96 或 192×192，透明底。
- SVG 必须 sanitize：去 `<script>`、`<foreignObject>`、`on*` 事件属性、外链 `href`，只留路径与基础图形；上传后转存为静态文件，不内联进页面。
- WebP 保留透明通道；单文件 ≤ 200KB，服务端统一转 PNG 兜底（老浏览器/账单出图）。
- 存 `/files/service-icons/`，`t_service_type.icon_path` 记录。
- 删除类型前检查是否有订单；有订单只能停用，不能删。

**接口**
- `GET/POST /api/admin/service-types`、`PUT /api/admin/service-types/{id}`。
- `POST /api/admin/service-types/{id}/icon`（multipart）。
- `PUT /api/admin/service-types/{id}/schema`。
- `GET /api/public/service-types`（客户端下单用）。
- 权限 `service.manage`。

**校验**
- 下单时服务端按 `form_schema` 校验必填/类型/下拉选项/长度；不信任前端。
- 订单存 `schema_snapshot + service_data`；详情按快照渲染。
- 不允许多余字段、不允许把费用字段放进 schema。

**验收**
- 后台新增"宠物接送"：上传图标、配置宠物类型/体重/是否笼子，保存后电话录单和客户端都出现；下单能填、能存、详情能看。
- 停用后新单不再出现，历史单正常显示。
- 上传带脚本的 SVG 被拒或清洗。

**风险**
- 动态表单容易做成"万能表单"，第一版只做 8 种字段（与商家自定义字段同一套），不做计算公式/联动。
- 图标上传要防 XSS；服务类型 `code / form_kind / flow_kind` 一旦有订单不可改；`name / icon / schema / 默认费 / 启停` 可改。

### R9 商家也在用户表中管理；类目多选；商家字段可新增

**原型现状**
- 商家是独立实体；用户管理里勾"商家"只是绑定已有商家，不能配类目。
- 商家新增在设置页，和用户管理两套入口。

**目标**
- 商家账号就是用户：手机号+密码登录，角色含"商家"。
- 新建/编辑用户时勾"商家"，展开门店信息：店名、**类目（多选，至少一个）**、电话、地址、备货超时，以及后台配置的自定义字段。
- 保存时一个事务里完成：用户 + 商家角色 + 门店档案 + 类目关系。
- 商家列表按多类目筛选/展示；类目和商家自定义字段在设置里维护。
- 从 R1 进来的"待完善商家"也在这里补全。

**数据模型**
- `t_merchant_category`：`id, code, name, sort_no, enabled`。
- `t_merchant_category_rel`：`merchant_id, category_id`，唯一键 `(merchant_id, category_id)`；一个商家多个类目。
- `t_merchant` 增加：
  - `status`：`pending` 待完善 / `active` 正常 / `paused` 暂停；

  - `extra_json`：自定义字段值；
  - `owner_user_id`：主账号（可空，多员工后续再加）。

**用户表单**
- 角色多选：管理员、骑手、商家、客户。
- 账号字段：登录手机号（`t_user.phone`，11 位）；门店电话可以另填（可同号，`t_merchant.phone`）。
- 勾"商家"后显示：
  - 店名（默认用户名）
  - **类目（多选，至少一个）**
  - 电话、地址、备货超时
  - 后台配置的自定义字段（按 `t_merchant_field` 渲染）

  - 提示"历史订单仍关联该门店，门店档案不会删除"；

### R11 账单出图：生成图片，不生成 PDF

**现状**
- 原型/旧方案用浏览器打印（`window.print`），产出 PDF 或打印对话框。

**目标**
- 点「账单」→ 生成 **PNG 图片**；可预览、保存、分享。
- 不调用 `window.print()`，不生成 PDF，不弹打印对话框。
- 手机优先调系统分享；不支持则下载图片。

**实现**
- 前端把账单 DOM 渲染成 PNG：
  - 2x 分辨率，宽度 750–1080px；
  - 用 `html-to-image` / `dom-to-image` 一类库，或手写 canvas；
  - 中文字体用系统字体，避免服务端缺字。
- 交互：
  1. 点「生成账单图片」；
  2. 显示图片预览（可缩放）；
  3. 按钮「保存图片」「分享账单」；
  4. 分享用 `navigator.share({files})`；不支持则 `<a download>`。
- 图片内容：
  - 品牌头：完整 logo（`bill-header-1200x240.png`）+ 订单号 + 日期；
  - 客户姓名（备注）+ 手机号；
  - 商家组（多商家时逐组列货款）；
  - 货款、跑腿费、附加费、优惠、应收、已收、未收；
  - 收款记录；
  - 底部「马儿跑得快，诚信赢天下」+ 生成时间。
- 不做二维码/电子签章（本期）。
- 服务端可选：`GET /api/admin/orders/{id}/bill-image` 返回 PNG，作为前端渲染失败兜底；不是主路径。

**验收**
- 点账单 → 出 PNG，浏览器不弹打印框；手机能保存/分享。
- 图片金额与页面/台账一致；多商家组逐组列货款。
- 长账单（20+ 收款）能完整出图，不被截断。

**风险**
- iOS Safari 的分享文件支持有限；必须有下载兜底。
- 长图渲染内存/清晰度；限制单图高度，必要时分页成多张图片（本期先不做）。
- 引入前端截图库会增加包体；优先选轻量方案。

## 6. 验收清单（增量）

### 多商家
- 客户一单 2 家店 3 件物品；下单成功；调度台两组。
- 商家 A/B 各看各的；骑手按组取货（0 和 92.40）；**全部取齐才允许配送**。
- 自由填写"楼下王记水果"生成待完善商家；不进常规搜索；补类目/电话后转正式；订单不阻塞。
- 账单合计 = 各组货款 + 跑腿费 + 附加费 − 优惠 + 调整。

### 改单/补商家
- 无商家订单补商家 → 通知 → 取货。
- 改地址/跑腿费留痕；已取货改货款被拒；已结单改金额被拒。

### 0 元/口语化
- 0 元取货成功、账单显示 0.00、取消不要求追回。
- 商家退钱/补给商家/给客户免掉三种方向金额正确；界面不出现"冲正/减免"。

### 收款
- 微信/支付宝/现金/欠款四种；欠款不写 payment，整单计入该客户账单。
- 部分收款（微信 50/应收 96）→ 流水 50、账单 46。
- 欠款 + 实收 50 被拒绝。

### 账单
- 默认今天（北京时间 0 点切）；今天 23:59 结单算今天，00:01 算明天。
- 今天跑腿费、昨天跑腿费、账单合计三个数固定；年月筛选只影响下面两张表。
- 订单表货款/跑腿费分列；订单区块与流水区块合计一致。
- 客户账单页"累计收回"= 全部 payment 合计 − 退款。

### 服务类型
- 后台新增"宠物接送"：图标 + 字段；两端出现；下单/详情；停用；SVG 安全。

### 商家用户
- 新建商家用户：类目多选（至少一个）+ 自定义字段；保存后门店+角色+登录一次完成。
- 类目新增/停用可用；商家列表按多类目筛。
- 待完善商家补全后转 active；同名/同电话合并。
- 历史商家迁移：旧文本类目映射到关系表；只有座机的标记未开通账号。

### 移动端（R10）
- 390×844 完成：录单（多商家）、取货、结单收款、看账单、登记还款、加商家用户，全程不横向滚动。
- 主要按钮单手可点；底部操作条不被 home indicator 挡住。
- PC 1440 下不出现手机布局拉伸变形。

### 账单图片（R11）
- 点账单 → 生成 PNG；浏览器不弹打印框，不生成 PDF。
- 手机能保存/分享；iOS 不支持分享文件时能下载。
- 图片金额与页面/台账一致；多商家逐组列货款；长账单不截断。
