# 05 · 安全（Security）

> **对应审查条目**：C4 文件安全 + F12 安全验收 + A8 权限隔离。
> **原则**：权限从身份上下文取、入口即分权、凭证文件边界明确。
> **注意**：`docs/design.md` 的鉴权章节描述的是**旧机制（免登令牌 + staff 角色）**，B2 改为全员手机号登录后已过时。本文以当前代码为准，差异记入 07-gaps.md G18。

---

## 1. 身份认证

### 1.1 当前机制（`CONFIRMED`）

- 全员手机号 + 密码登录（`B2` 已删免登令牌）；
- 会话令牌通过 `X-Auth-Token` 头传递，Sa-Token 管理；
- 多角色：一个手机号可同时是客户/骑手/管理员/商家，权限全在 `t_user_role`（多对多）；
- 工作区切换：选定当前角色后，后续操作按该角色 scope 执行。

### 1.2 按路径分权（`CONFIRMED`）

| 路径前缀 | 身份来源 | 数据范围 |
|---|---|---|
| `/api/admin/**` | 管理员会话 | 平台级，按权限码授权 |
| `/api/m/**` | 商家会话 | `scope_merchant_id` |
| `/api/r/**` | 骑手会话 | 当前骑手 user_id |
| `/api/c/**` | 客户会话 | 当前客户 user_id |
| `/files/**` | 静态文件 | 小票、送达照、凭证；不再有 `/api/public/**` 客户免登链接 |

## 2. 权限隔离与越权防护（`CONFIRMED`）

### 2.1 核心规则

1. `merchant_id`、`rider_id`、`customer_id` **一律从身份上下文取**，绝不接受前端传入；
2. 商家端每个写操作先做 `belongCheck`（归属校验）——一张泄露的链接不能改别人家的单；
3. 骑手只能操作指派给自己的单（`belongCheck`）；
4. 客户只能访问自己的订单和账单；
5. 多商家订单：商家只访问自己的组（02 §A8.1）。

### 2.2 权限码一致性（`CONFIRMED`）

- 权限码清单唯一权威定义 = 02 §A8.2 的 16 项；
- 代码种子（V3/V6，V9/V10 删除冗余项）、后端鉴权、前端菜单必须逐项一致；
- 新增权限码必须先改 02，再改代码；
- 后台接口权限由 Controller 方法上的 `@RequirePerm` 声明（见 `security/RequirePerm.java`），`AuthInterceptor` 从 `HandlerMethod` 读取；未标注接口一律拒绝，避免路径字符串匹配导致的漏配与错配。`super_admin` 绕过权限码矩阵；
- 用户管理页统一维护账号、角色和档案（客户备注/地址、商家门店），不再有独立"主数据管理"入口；商品由管理员在「系统配置 → 默认商品」统一维护，商家不参与商品建档；创建带 `customer` 角色的用户会同时建档 `t_customer`。

## 3. 文件安全

### 3.1 上传（`PROPOSED`，见 04 §C4）

- MIME 白名单：图片（PNG/JPG/GIF/BMP/WebP）+ 语音；SVG 默认禁止（U-05 待裁决）；
- 扩展名 + 真实文件类型双重校验，**不信任客户端 MIME**；
- 单文件 ≤ 8MB；每类附件数量上限待定（F2）；
- 文件名用随机串，不用用户输入；
- 存储路径 `normalize()` 防目录穿越，并校验最终路径仍在上传根目录内。

### 3.2 下载与访问

- `/files/{path}` 由 nginx 直发，不经过 Java；
- **凭证文件是"URL 即能力"（capability URL）**：知道 URL 就能看到图片；
- 边界：对外暴露前应在 nginx 加 Referer/内网限制，或改签名 URL（`PROPOSED`）；
- 文件访问需权限校验（C4 规则 6）。

### 3.3 文件生命周期（`PROPOSED`，F21）

- 防止孤立文件：订单取消/删除时的附件清理策略待定义；
- 防止误删：清理必须有审计记录。

## 4. 注入与脚本防护（`PROPOSED`，F12 安全验收项）

| 威胁 | 防护 | 验收 |
|---|---|---|
| SQL 注入 | MyBatis-Plus 参数化查询，禁止拼接 SQL | 自动化安全测试 |
| XSS | 客户输入转义；SVG 脚本清洗（U-05）；前端不 `v-html` 不可信内容 | 安全测试 + 人工审查 |
| 越权 | §2 归属校验 | 自动化 API 测试 |
| 目录穿越 | 路径 normalize + 根目录校验 | 安全测试 |

## 5. 审计与可追溯（`CONFIRMED` / `PROPOSED`）

- `t_audit_log`：记录 actor、http_method、path、response_status、时间（`CONFIRMED` 已有）；
- `t_order_edit_log`：改单留痕（谁改了什么、为什么）；
- `t_order_status_log`：状态流转留痕；
- 财务调整必须记录操作人/时间/金额/原因/关联订单（I-1 规则 4）。

---

## 6. 数据保护（`PROPOSED`）

- 数据库备份用 `mysqldump`（因 `t_ledger_entry` 有 UPDATE/DELETE 触发器，不能用 DELETE 清库，见 08 §F18）；
- 明文密钥不得进入代码/配置仓库（D3 部署验收项）；
- 客户手机号等敏感信息在日志中脱敏（`PROPOSED`）。

---

## 7. 安全验收清单（映射 F12）

对应 06-acceptance.md 的安全类验收项（P0）：
- 文件上传：exe 改 jpg 被拒、超大文件被拒、SVG 策略符合裁决；
- 越权：客户 A 访问客户 B 订单被拒、商家 A 改商家 B 订单被拒；
- SQL 注入 / XSS / 目录穿越测试通过；
- 审计日志完整；
- 无明文密钥泄漏。
