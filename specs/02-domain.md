## A1 · 不变式（三条硬规则）

| 编号 | 规则 | 领域层落地要点 | 状态 |
|---|---|---|---|
| I-1 | 实际货款不可变 | `goods_real_fen` 写入后 Service 拒绝覆盖；争议走 `adjust`/`waive` 流水；预估 `goods_est_fen` 取货前可改 | `CONFIRMED` |

## A2 · 状态机（5 状态）

### A2.1 状态定义（重新表述业务含义）

`CONFIRMED`（5 状态本身）；下列"定义"列为本次精确化，`PROPOSED`。

| 状态码 | 标签 | 业务定义（精确化） | 主要触发角色 | 终态 |
|---|---|---|---|---|
| `PENDING` | 待接单 | 订单已创建，等待系统/管理员指派履约人 | 系统 / 管理员 | 否 |
| `PICKING` | 取货中 | 骑手已接单，正在取货**或准备服务**（对无实物类业务即准备履约） | 骑手 / 管理员 | 否 |
| `DELIVERING` | 配送中 | 已完成取货，正在配送**或履约执行中** | 骑手 / 管理员 | 否 |
| `FINISHED` | 已完成 | 订单履约完成，且资金规则已确认（垫付清算、应收结清或挂账） | 骑手提交，按规则确认 | 是 |
| `CANCELLED` | 已取消 | 订单取消，按授权规则执行，涉及垫付的已清算 | 客户 / 管理员 | 是 |

> 状态数量维持 5 个不变。历史 V4 迁移把 7 状态合并为 5（去掉"待备货/备货完成"，合并"已送达+结单"为"配送完成"）。**不直接增加状态**。

### A2.2 履约动作与状态解耦（关键设计约束）

**问题**：五类服务并非都有"取货"和"配送"两个阶段。代办可能只有执行服务，没有物品取货；接送/代驾是"接到人/上车"，不是"取货"。

**决策（`PROPOSED`）**：
1. 订单状态与履约动作**适度解耦**：
   - `PICKING` 代表"已接单、准备履约"；
   - `DELIVERING` 代表"履约执行中"；
2. **不同服务类型配置不同的页面文案与操作名称**（如代驾显示"前往接车 / 已接到客户 / 送达目的地"），数据库状态码不变；
3. 文案配置随 `form_kind` / `flow_kind` 走（见 A6），不新增数据库状态；
4. **是否增加 `IN_SERVICE` 状态**：`UNDECIDED`（见 U-09）。判断标准——若存在独立于"取货/配送"的**服务执行阶段**且不复用现有状态可表达，才增加；若只是换页面文案，**不增加**数据库状态。

### A2.3 状态转换权限矩阵（`PROPOSED`，需补代码实现）

| From \ To | PENDING | PICKING | DELIVERING | FINISHED | CANCELLED |
|---|---|---|---|---|---|
| **PENDING** | — | 管理员/调度（派单） | 禁止 | 禁止 | 管理员、客户（未接单） |
| **PICKING** | 禁止 | — | 骑手/管理员（取货完成） | 禁止 | 管理员（需清算垫付） |
| **DELIVERING** | 禁止 | 禁止 | — | 骑手提交；管理员按资金规则确认 | 管理员（需清算垫付） |
| **FINISHED** | 禁止 | 禁止 | 禁止 | — | 禁止（冲正/收款不改状态） |
| **CANCELLED** | 禁止 | 禁止 | 禁止 | 禁止 | — |

### A2.4 非法状态转换拒绝规则（`PROPOSED`）

1. 所有流转必须过 `OrderService.move()`，唯一真源是 `OrderStatus.TRANSITIONS` 白名单；非法流转抛 `BizException`，中文文案直接展示。
2. **终态不可回流**：`FINISHED` 不得直接返回 `PENDING`（U-09 关联）；`CANCELLED` 不可复活。
3. 任何进入 `FINISHED` / `CANCELLED` 的转换，必须先通过资金前置校验（I-3 垫付清算；应收结清或挂账）。
4. 转换必须写 `t_order_status_log`（from/to/action/actor/role/reason/time）。

> **实现状态**：白名单与 `move()` 已实现（`IMPLEMENTED`）；权限矩阵与终态回流的**角色级**校验尚未实现（`IMPLEMENTATION_GAP`）——当前代码只校验状态白名单，不校验"该角色是否有权做此转换"。

## A3 · 金额口径

### A3.1 两个应收概念（本次拆分，`PROPOSED`）

**旧口径（易双重计算）**：
```
应收 = 货款 + 服务费 + 附加服务费 − 优惠 + 冲正 + 调整
```

**新口径（推荐）**：
```
订单基础应收 = 货款 + 服务费 + 附加服务费 − 优惠
最终应收     = 订单基础应收 + 经批准的订单调整
```

**防双重计算规则（`PROPOSED`）**：
- 若某笔调整已通过 `t_ledger_entry`（CHARGE/ADJUST/WAIVE）记账，则**不得再重复计入订单应收**；
- 订单视图展示的"应收"必须与 `ledger` 派生出的应收一致，二者取其一为权威（推荐 ledger 为权威，见 I-2）；
- 术语统一：数据库字段统一为 `service_fee_fen / extra_fee_fen`（服务费/附加服务费）；界面按业务场景显示不同名称，见 A9.2。

### A3.2 优惠（discount_fen）

- **一期暂不启用优惠功能**，不实现整套优惠券体系（`CONFIRMED` 方向，字段预留见 03 §B1）。
- 不因为 Marketing 是未来模块就提前建设。
- `discount_fen` 字段即使存在，一期必须恒为 0，API 不接受非零值。

### A3.3 金额存储

- 所有金额以 **分（BIGINT）** 存储，禁止 decimal/float 参与运算（`CONFIRMED`）。
- 前端只在输入/展示层做元↔分转换。

## A4 · 时区（7 条规则，`PROPOSED` 升级）

原 `ADR-0004` 只规定"统计切日用 Asia/Shanghai"。本次升级为 7 条：

1. 业务时区固定为 `Asia/Shanghai`；
2. 数据库时间字段统一存储 UTC（与现状有差异，见 U-03）；
3. 所有业务日期统计使用北京时间；
4. 禁止依赖 JVM 默认时区；
5. 前端显示时间必须明确使用北京时间；
6. 定时任务必须显式指定时区；
7. Docker 容器、数据库和应用程序的时区配置必须明确。

**NAS 部署特别约束**：NAS 系统设置为 UTC 或 +08:00，**不应改变应用程序业务时区**；应用必须独立配置时区。

> **U-03（待裁决）**：规则 2 要求 DB 存 UTC，但当前代码用 `LocalDateTime` + 本地 DATETIME，且 `HealthService` 用 `LocalDate.now()`（服务器默认时区）。改成 DB 存 UTC 是大改动，需评估。本宪法建议：**应用层显式 `ZoneId.of("Asia/Shanghai")` 做统计切日先落地（`IMPLEMENTATION_GAP`，B4），DB 存 UTC 作为独立议题评估**。请用户裁决。

## A5 · 多商家组规则

> **实现状态**：`DEFERRED`（用户此前明确"B3 先不做"）。规格完整定义，代码暂不实现。见 U-07。

### A5.1 规则表（`CONFIRMED` 业务规则 / `DEFERRED` 实现）

| 事项 | 推荐规则 |
|---|---|
| 配送条件 | 所有有效商家组完成取货后才能进入 `DELIVERING` |

- 从 1 开始；

- 尚未取货时允许调整；

- `seq` 在订单内有唯一性约束。

### A6.1 服务类型按实际需求增减（`CONFIRMED`）

不再固定"五类业务都做"。`t_service_type` 是服务类型字典，后台可新增、改名、停用或启用；下单页只展示 `enabled = 1` 的类型，历史订单按订单快照渲染，不受类型停用影响。

| code | 种子名称 | flow_kind | 商家 | 垫资 | 默认启用 |
|---|---|---|---|---|---|
| `buy` | 代买 | `buy` | 有 | 有 | 是 |
| `pickup` | 代取送 | `service` | 无 | 无 | 是 |
| `errand` | 代办 | `service` | 无 | 无 | 是 |
| `transfer` | 接送 | `service` | 无 | 无 | 否（V6 停用，按业务需要启用） |
| `driver` | 代驾 | `service` | 无 | 无 | 是 |

> **U-01 已裁决**：以"按实际需求增加或取消业务"为准，不强制五类齐全；`enabled` 是唯一启用开关。新增类型必须同时配置 `flow_kind`、`base_fee_fen` 和专属字段校验。

### A6.2 四层字段职责（`PROPOSED`，原来只有 code/flow_kind/form_schema）

| 字段 | 职责 |
|---|---|
| `code` | 服务类型唯一标识 |
| `flow_kind` | 决定业务流程（`buy` 需商家垫资 / `service` 标准无商家） |
| `form_kind` | 决定表单展示形式（内置版式：`buy`/`route`/`driver`/`blank`） |
| `form_schema` | 决定动态表单字段（JSON，版本化） |

**配置约束（`PROPOSED`）**：
1. `code` 创建后不可修改；
2. 已有订单引用的 `flow_kind` 不允许直接修改；
3. `form_kind` 可通过新版本配置调整，但历史订单必须保留原始快照；
4. `form_schema` 必须版本化（`schema_version`）；
5. 服务类型禁用后，不影响历史订单（历史单按快照渲染）。

### A6.3 计费（`CONFIRMED` 一期固定费用模式）

- 基础服务费（界面按业务显示为跑腿费/代办费/代驾费等）；
- 附加服务费；
- 管理员人工调整（走流水，见 A3）。

## A7 · 收款方式

### A7.1 字段语义重构建议（`PROPOSED`，见 U-02）

**问题**：`credit`（欠款）不是传统支付渠道，而是赊账/延期结算方式。把渠道和结算状态混在一个枚举里，未来加银行转账会混乱。

**建议拆分**：

| 类型 | 枚举 |
|---|---|
| 实际收款渠道 | `wechat`、`alipay`、`cash`、`bank_transfer`、`other` |
| 结算方式 | `immediate`、`credit` |

**仍采用固定枚举，不开放后台任意添加收款渠道**（`CONFIRMED`）。

> **U-02（待裁决）**：当前代码是四枚举 `wechat/alipay/cash/credit`（用户此前确认"四种收款方式"）。拆成"渠道+结算方式"是结构性改动，涉及 DB 字段、API、UI。请用户裁决是否在一期改造，还是保留四枚举、仅登记为未来优化。

### A7.2 欠款与多次收款规则（`PROPOSED`）

1. 欠款订单的实收金额 = 订单金额 − 创建欠款时的对应收款记录（**指创建欠款记录时的对应收款，而非订单历史累计收款**）；
2. 后续客户还款必须**单独记录**（`t_ledger_entry` PAYMENT，独立还款申报）；
3. 一笔订单允许多次收款；
4. 不允许修改已确认的收款记录，只能通过冲正处理。

> 上述规则与 01 宪法 I-2（余额由流水推导、不删流水）一致，属于对现有 `finish()` 单次收款模型的增强。当前 `finish()` 只在结单时记一次 PAYMENT（`IMPLEMENTATION_GAP`）。

  - `merchant_call` / `merchant_wechat` / `other` → `source = phone`（电话/商家发起）
- 若未提供 `source_channel`，默认 `source = phone`。
