## 0. 状态标签图例

全套规格统一使用下列标签。**每个重要条目都必须带标签之一**，禁止出现"既没确认也没标记"的裸规则。

### 0.1 问题分类（用于审查发现、需求条目）

| 标签 | 含义 | 判定标准 |
|---|---|---|
| `CONFIRMED` | 已经确认，不允许随意变更 | 用户在对话中明确拍板，或有 ADR 记录 |
| `PROPOSED` | 有明确建议，等待用户批准 | 本次审查新提出、尚未拍板 |
| `IMPLEMENTATION_GAP` | 业务规则已明确，但代码尚未实现 | 规格为 `CONFIRMED`，代码缺失 |
| `UNDECIDED` | 业务决策尚未完成 | 存在冲突、矛盾或信息不足，必须裁决 |

### 0.2 漂移状态（仅用于 07-gaps.md 的 Gx 漂移点）

| 状态 | 含义 |
|---|---|
| `CONFIRMED` | 业务规则已确认 |
| `IMPLEMENTED` | 代码已经实现 |
| `NOT_IMPLEMENTED` | 已确认但代码未实现 |
| `IMPLEMENTATION_GAP` | 代码实现与规格不一致 |
| `SPEC_GAP` | 规格本身缺少定义 |
| `UNDECIDED` | 业务决策尚未确认 |
| `DEPRECATED` | 已废弃，不再适用 |

> **两套分类法的关系（本宪法给出的裁决）**：§0.1 的四类是**全局语义层**——回答"这条规则是什么性质"；§0.2 的七态是**漂移跟踪层**——回答"这个 Gx 漂移点当前处在修复流程的哪一步"。一个漂移点可以同时是"底层规则 `CONFIRMED`、跟踪状态 `IMPLEMENTATION_GAP`"，二者不冲突。此裁决本身标记为 `PROPOSED`（见 U-08），待用户确认后固定。

### 0.3 实现状态（用于规则与实现脱节的场景）

| 标签 | 含义 |
|---|---|
| `IMPLEMENTED` | 代码已实现且与规格一致 |
| `DEFERRED` | 规格已定义，但按排期暂缓实现（如 B3 多商家） |
| `NOT_IMPLEMENTED` | 应实现但未实现 |

## 1. 三条不变式（硬规则）

这三条是财务业务的地基，**不可妥协、不可绕过、不可删除**。每次功能变更、每次重构都必须先核对是否触碰这三条。

### 不变式 I-1 · 实际取货货款不可变

**规则陈述**（精确化后）
1. 商家实际取货货款经确认后形成不可变记录；
2. 已确认的实际货款不得通过 `UPDATE` 直接覆盖；
3. 发生争议时，通过冲正、补收、减免等**独立流水**进行调整；
4. 每笔调整必须记录操作人、时间、金额、原因和关联订单；
5. 原始货款与调整记录必须永久可追溯。

**关键区分**：预估货款（`goods_est_fen`）≠ 实际取货货款（`goods_real_fen`）。
- 预估货款：取货前可调整（改单允许修改）；
- 实际货款：确认后立即锁定，只能追加流水。

**`NULL` 与 `0` 的语义**：`goods_real_fen IS NULL` = 未取货/未录；`goods_real_fen = 0` = 已确认无货款（0 元取货合法）。

**验证方式**：`OrderFlowTest` 中"已取货改货款被拒"用例 + 数据库 UPDATE 触发器 + `HealthService.issues()` 自检。
**状态**：`CONFIRMED`（规则 1–5 为本次精确化补充，不改变原意）

---

### 不变式 I-2 · 金额由流水推导，余额不可手改

**规则陈述**（精确化后）
1. 货款 ≥ 0，服务费 ≥ 0；
2. 客户订单金额 = 货款 + 服务费 + 冲正 − 减免；
3. 客户订单合计金额 = 客户相关订单金额之和；
4. 客户账单合计金额 = 客户订单合计金额；
5. 客户欠款金额 = 客户账单合计金额 − 客户已付款；
6. 收款、冲正、减免必须形成对应流水；
7. 欠款余额实时由流水计算，不允许人工直接修改余额；
8. 不允许删除已经生效的财务流水。

**性能优化边界（本次新增方向）**：未来可增加"账户余额快照"作为性能优化，但快照**只能是可重建的缓存**，不能成为独立的权威数据；权威数据永远是流水之和。
**状态**：规则 1–8 = `CONFIRMED`；快照机制 = `PROPOSED`

> **待裁决 U-04**：审查意见原文写"客户欠款金额 **<=0**；客户欠款金额 **>=0**"，两者同时成立意味着欠款恒为 0，与实务矛盾。结合上下文（"客户支付 120 元则减去 20 元欠款，如果没有欠款则产生 20 元预存"），本宪法按 **欠款 ≥ 0，多付部分转预存** 理解。请用户确认后固定为 `CONFIRMED`。

---

### 不变式 I-3 · 垫付未清算不得终态

**规则陈述**（精确化后）
1. **垫付定义**：取货完成确认货款金额并向商家支付后，订单将预估货款金额改为实际货款金额，此时该货款即为骑手垫付；完成配送时向客户收取费用，用于交代垫付费用支付金额。
2. **计例**：货款 90 元 + 服务费 10 元 = 订单金额 100 元。客户付 100 元 → 订单完成；客户付 80 元 → 产生 20 元欠款；客户后续付 120 元 → 先冲 20 元欠款，剩余 20 元若无欠款则转预存。
3. **欠款公式**：欠款 = 订单金额 − 客户实际支付金额。
4. **终态约束**：垫付未交代（追回或认损）的订单不得进入终态 `FINISHED`。
5. **0 元取货**：不生成垫付记录、不产生垫付追回任务、不允许因零元取货生成虚假财务流水。

**验证方式**：`OrderFlowTest` 取消清算用例 + `HealthService.issues()` 垫付核对。
**状态**：`CONFIRMED`

## 2. 本次审查的五条总原则

后续所有规格补充、代码评审、验收设计都必须遵守。

| 原则 | 具体要求 |
|---|---|
| **业务优先** | 以已确认的业务需求为依据，而不是盲目以代码为准 |
| **数据一致** | domain、data-model、api、acceptance 必须相互一致 |
| **向后兼容** | 修改数据库时必须考虑已有数据和迁移路径 |
| **最小复杂度** | 不为尚未实际开展的业务提前建设复杂功能 |
| **可验证** | 每条重要规则必须有对应测试或验收方法 |

**落地约束**：
- "业务优先"意味着：代码实现了某功能 ≠ 该功能就是需求；新增功能不得因为"代码里已有"就跳过业务确认。
- "最小复杂度"意味着：营销/优惠券/预存体系、多租户、万能表单、复杂计费公式等未来能力，一期一律不建。
- "可验证"意味着：02–04 中每条 `CONFIRMED` 规则，必须在 06-acceptance.md 有对应编号 Axx 或测试映射。

## 3. 关键纪律

1. **绝不把"代码已实现"等同于"业务规则已确认"。** 代码状态只由 07-gaps.md 跟踪，不得反向写入 01/02 当作需求依据。
2. **规格先行**：新功能先改 specs（本体系）→ 评审 → 再改代码 → 测试映射到验收编号 → 提交信息引用规格编号。
3. **单一真源**：权限码清单、服务类型清单、状态码清单各自只有一个权威定义处（见 02 §8 / 02 §6 / 02 §2），代码种子、后端鉴权、前端菜单必须与之逐项对齐。
4. **不回避冲突**：发现规格之间、规格与代码之间的冲突，必须显式记为 `UNDECIDED` 并给编号，不得在文档里"各自表述、假装一致"。
5. **迁移只加不改**：已执行的 Flyway 迁移文件永不修改；结构变更一律新增迁移脚本（详见 08 §F18）。

## 4. 业务边界与一期范围

**一期必做（P0 业务闭环）**：订单全流程、取货/垫付/收款、欠款与冲正、权限隔离、数据一致性、文件上传安全、部署与备份恢复。

**一期定义但不实现（`DEFERRED`）**：
- B3 多商家订单（规则见 02 §5、03 §2，实现状态 `DEFERRED`——用户此前明确"先不做"）。
- 营销/优惠券体系（`discount_fen` 字段一期不启用，见 02 §3）。
- 账户余额快照（见 I-2）。

**明确不做**：多租户、微服务、Redis、消息队列、微信支付在线扣款、预付、电子签章、二维码。

> 服务类型不再固定为"五类都做"：后台按实际需求增加、停用或取消业务，客服端只展示 `t_service_type.enabled = 1` 的类型。当前种子包含代买、代取送、代办、接送、代驾，其中接送默认停用（V6），是否启用由业务决定。见 02 §A6.1。

## 6. 变更流程

1. 新功能：先改 specs（对应 01–08）→ 评审 → 再改代码 → 测试映射到验收编号 → 提交信息引用规格编号（如 `feat(B3-T3): ...`）。
2. Bug 修复：先在规格中补充/修正条目（或新增 ADR），再修代码。
3. 规格与代码冲突：不得"顺手"改代码绕过规格；必须先更新规格并记录 ADR，再改代码。
4. 本文 §5 的 U 编号一旦裁决，必须在 ADR 目录新增对应记录，并同步更新引用它的所有文档。
5. 提交信息约定：`<type>(<spec-id>): <summary>`。
