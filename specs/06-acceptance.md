# 06 · 验收标准（Acceptance）

> **对应审查条目**：D1–D4。
> **原则**：可验证——每条重要规则必须有对应测试或验收方法。
> **关键口径（用户强调）**：P0 是"系统上线前必须通过"，**不代表现在所有 P0 功能都必须立即开发完成**。验收分类与迭代排期是两件事。

## D2 · 测试映射（每条验收必须有证据）

### D2.1 推荐映射方式

| 验收类型 | 测试方式 |
|---|---|
| 金额计算 | 自动化单元测试 |
| 订单状态转换 | 自动化集成测试 |
| 权限隔离 | 自动化 API 测试 |
| 多商家流程 | 自动化 E2E 测试 |
| 文件上传安全 | 自动化安全测试 + 人工审查 |
| UI 展示 | 人工验收 + E2E |
| Docker 部署 | 部署测试 |
| 备份恢复 | **实际恢复演练** |

> 每条验收标准必须有测试证据，但不要求全部自动化。

### D2.2 测试追踪字段（`PROPOSED`）

每条 Axx 映射增加以下字段，形成可追溯矩阵：

| 字段 | 说明 |
|---|---|
| `acceptance_id` | 验收编号（Axx） |
| `requirement_id` | 对应需求/规则编号（A1–A9 / Bx / Cx / Ixx） |
| `test_file` | 测试文件路径 |
| `test_case` | 测试用例名 |
| `test_status` | pass / fail / not_covered |
| `evidence` | 证据（截图/日志/测试报告路径） |

> 目标：A1–A31 每一条都能找到对应验证证据。未覆盖项（test_status=not_covered）必须显式列出，不得空白。

## D4 · 性能验收（新增，P1）

A6 的 300ms 目标保留，但必须定义测试条件才可执行：

| 条件 | 定义（`PROPOSED`） |
|---|---|
| 指标 | **普通订单查询 P95 < 300ms** |
| 数据量 | 可重复生成的虚构数据集（建议 ≥500 条订单，与 A6 一致） |
| 硬件 | 明确 NAS 的 CPU、内存、数据库配置（部署时填写） |
| 并发数 | 明确并发请求数（建议单用户基线 + 小并发） |
| 查询条件 | 明确查询参数（状态筛选 + 关键词检索） |
| 统计口径 | 是否含数据库查询 + 接口序列化（建议：含，端到端计时） |
| 统计方法 | P95（不用最大值，避免偶发抖动误判） |

> 这样才是可执行的性能验收标准，而不是一句没有测试条件的性能承诺。

## D5 · 验收执行纪律（`CONFIRMED`）

1. P0 项必须全部通过才算上线就绪；
2. `DEFERRED` 的多商家项（A13–A17, A28）虽属 P0 类别，但按排期暂缓——其"未覆盖"状态须显式标注，不得伪装为通过；
3. UNDECIDED 项（如 A26 SVG）在裁决前不得标记最终状态；
4. 每次发布前更新 D2.2 追踪矩阵，未覆盖项清零或有明确豁免记录。
